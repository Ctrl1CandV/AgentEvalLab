## WP0.2 Evidence table

- `src/analysis/evidence.ts` and `scripts/evidence-table.ts` (`npm run evidence`) read every suite run (`runs/suites/*/suite.json`, the latest run of each plan, its frozen plan and worktree) and every plain run under `runs/`, and write `docs/evidence/V1_EVIDENCE.md` with a JSON twin.
- One row per model, task package, run directory **and grader version**. Each trial's append-only score runs are grouped by the grader version that produced them, so a re-graded run shows its old and new numbers side by side (for example T1 0.6.0 under graders 1.7.0 and 1.7.1). Scores reuse the suite scorer (`trialUnit`, `trajectoryUnit`, `familyResults`), restricted to the family's scored items or levels for suite runs; trajectory scores read the manifest the run saw (the frozen worktree, or `git show <commit>:<path>` checked against the recorded manifest hash).
- Protocol per row: budget per trial, or per stage and trajectory; context policy; thinking level in the label; stated budget (suite plans). Coverage per row: infrastructure failures, trials not run, unscored trials, trials without a score run under that grader, budget stops.
- Dry-run suites (AE `20261023-192640-dev-87c1`) are listed with their smoke result and no rows. Interrupted trajectory runs and superseded attempts are listed under "Run directories without rows".
- "Configurations in the current suites" checks whether the templates the suite files point to now were ever run with exactly that package version, context policy and budget: **T2 at 10M** and **AE** are never run.
- The review cross-reference section resolves every number of the review's §2 table to its rows: all ten claims are found and match (T1 94.3/85/20 is the grader 1.7.1 re-grade; the original 1.7.0 grading read 89.8/84.0/18.1).
- Test: `tests/evidence.test.ts` (a fixture run re-graded under a second grader version gives two rows; a dry-run suite gives none).

## WP0.3 T2 coverage hole

- **Reproduced** offline under grader 1.1.0: a correct fn1 or fn2 day, then `begin R999` and a balanced 1,000,000.00 EUR entry on 1100/4000, scored 45/45 with integrity `consistent`.
- **Fix** (t2-finance-desk grader 1.2.0, task 0.3.0 unchanged, commit `3501fe3`). Two critical checks of the whole day, beside the unchanged per-request diagnostics:
  - `coverage`: every changing command (`post`, `set-plan`, `set-status`) belongs to exactly one request of the day, in the order given. Violations: unknown request, change before the first `begin`, reopened request, out-of-order request; without markers, a change no request owns. It traces to manual §8 ("Handle them in the order given … run `ledger.py begin R3` … change nothing for a request once you have begun the next … do not post anything else"). It needs at least one changing command, so the null agent earns nothing.
  - `end-state`: the books from the original start equal the oracle's correctly handled day (same footprint, statuses, and a plan the books allow).
- **Self-calibration** (`logs/self-calibration-0.3.0-grader-1.2.0.log`, 103 scenarios, PASS): the R999 reproduction and a change before the first `begin` lose `coverage` and `end-state`; reopening the plan request and swapping R10/R11 lose `coverage` only; alternative flows (repeated `begin`, an unknown request begun without changes, the plan revised within its request, no markers at all) keep every check. `tests/t2-coverage.test.ts` runs it under `npm test`.
- **Item files are byte-identical** (builder `--reuse-days`); plans `experiments/t2-finance-2026-10/{dev,full}.eval.json` re-pinned; package check passes.
- **Scan of recorded trials** (read-only, the 1.2.0 coverage rule over every audit log): no violation in any trial of 0.1.0 (`4b33`), 0.2.0 (`a7e7`) or 0.3.0 (`9f16`). The hole produced no recorded score, as the review found for `9f16`.
