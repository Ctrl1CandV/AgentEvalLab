## WP2.4 Harness features (committed first)

Committed before WP2.1–2.3 because it touches only code, while the Phase 1 trajectory test was still running against the package directories. Includes the score-model addition WP2.2 needs.

- **Runtime mounts** (CODE §4). `scripts/sandbox_exec.py --mount SOURCE:/runtime/<name> --env NAME=VALUE` binds a directory read-only at a fixed path and sets its environment; a target outside `/runtime` and the reserved names (`HOME`, `TMPDIR`, ...) are refused. `isolatedCommand(..., runtime)` passes them; `execute_command` binds the item's mounts (`runtimeMounts(descriptor, item)`), and a grader request carries `runtime` (sources, targets and the environment) for graders to pass to the launcher. Without the sandbox nothing is bound and the environment names the sources. Every file under `runtime/` is a hashed trusted file (the harness and `task_packages.py` both check the file set); an item may select its mounts (`mounts`). Mounts are refused in trajectories (none needs them).
- **Answer-only profile** `none`: no tools, a single reply. Accepted in manifests and plans, needs no trusted execution, refused in trajectories. The condition fingerprint records it with no tool names.
- **Repository workspaces** (CODE §5, `src/evaluation/repository.ts`). An item's `repository` (a hashed archive under `private/`) is unpacked into `repo/`, committed once under a fixed author and date (every file of the archive, ignored ones too), and copied bare outside the workspace. After the session the change is read against that commit through the harness's copy, so it survives the model rewriting or deleting the workspace's `.git`, and counts the model's own commits. It is saved as `submission.patch` (10 MB at most; more is a resource-limit failure), passed to the grader as `patchRef`, and the repository stays out of the artifact snapshot (whose 1,000-file limit a real repository would break). Design detail added to CODE §5: the issue is item material (`prompt.md`, `public/ISSUE.md`), not a file the harness writes.
- **Per-item headlines** (for WP2.2). E4 holds contract items (basic) and compress (an open-ended bridge) under one grader; TASK_LIBRARY §2 reports them as separate families. `scoreModel.primaryByItem` gives an item its own primary, a metric group may name the `items` it applies to, and anchors are required only for the metrics a task is scored on. A suite family whose items have different headlines is refused (`SUITE_FAMILY_MIXED_PRIMARY`), at generation and at reporting.
- Tests: `tests/runtime-workspace.test.ts` (a mount visible, read-only and with its environment, also through `execute_command`, and absent without the mount; the `none` profile offers the model no tool and is recorded so; a repository fixture package whose grader applies the patch, restores the test file and runs the gold tests with the runtime mount: a real fix committed by the model passes although it also weakened the tests, a weakened test file alone fails, also after deleting `.git`); `tests/manifest-v2.test.ts` (repository and mount refusals; per-item headlines and item-scoped metric groups); `tests/scoring.test.ts` (a contract item and an open-ended item of one package). All 111 tests outside the trajectory file pass.

Shared code: a score-model metric may be declared for some items only (`metrics[].items`); a grader must report it for those, and a task is scored only on metrics its grading reports (`INVALID_SCORE_ITEMS` otherwise). Tests added.

**Noise tests** (PROTOCOL §9), each in the package's `logs/`:

- E4 speedup: oracle, DictReader and strptime variants, quiet against all 20 cores busy: identical verdicts, ratio changes 1.0–4.3% (tolerance 15%). One self-calibration expectation corrected: the `ascii-digits-only` mutant is 12% slower in CPU time than the reference and stops at `speed-1.5`; under wall time it had passed `speed-1.1` by noise.
- E3 S6: ref-a and ref-b, identical verdicts, ratio changes 4.3% and 0.8% (tolerance 15%).
- **E2 routes: fails under full load.** With 5 busy processes on 20 cores the LNS reference's `routeShare` moves 0.009 with no label change (pass at the declared 0.03); with all 20 cores busy it loses 0.052 and three rung labels. The cause is the contract's wall-time limit: a time-bounded search does less work when its core is shared. The lock serialises routes gradings but not other load. Making the limit CPU time would change the contract, and so the task version, which a bridge should not do. **Open for the user** (Phase 2 report).

**Re-grades and what they showed** (with the harness's `--regrade` and `--regrade-trajectory --scope final`):

- E4 0.5.0, 8 trials: no verdict changed under CPU timing. v2 outcomes: compress deepseek-flash 0.927 and qwen3.8-flash 0.818 normalised (valid), the other three invalid (0); speedup mimo-v2.6-flash resolved (ratio 0.819), deepseek-flash and qwen3.8-flash not (their `quirks` failures from grader 1.5.0), qwen's ratio 0.756 just short of the 0.75 label.
- E3 0.5.0, the final snapshot of 10 trajectories: one label flip, deepseek-flash b319 `scale.speed-1.1` fail → pass (CPU ratio 1.013); resolved: b319 both models and c750 deepseek-flash; trajectories that never reached S7 are unresolved (their missing checks count as failed).
- E2 0.5.0 routes, 15 graded trials under 1.6.0: a few rung labels moved with the wall-time noise (at most five per trial, in both directions), as the noise test predicts. **A design defect showed:** with the README critical, 8 of the 15 deliveries, deepseek-flash at 0.904 and mimo-v2.6-flash at 0.886 of the way among them, had a primary of 0 for a missing `README.md`. A documentation file decides nothing about the routes a program plans, and holding the headline hostage to it is the kind of format trap principle 3 rules out. Grader 1.7.0 makes the README a non-critical diagnostic for every E2 item and gives routes a validity check of its own, `routes-feasible` (a feasible plan for at least one hidden instance), so a null delivery is still invalid. Re-graded again under 1.7.0.
- E2 routes under 1.7.0, 15 trials: `routes-feasible` passes for 13 (the two that time out on every instance fail it). The re-grade also confirmed the noise finding on a lightly loaded machine: mimo-v2.6-flash's delivery in `runs/a69d9886-…`, which plans for about 9 s against the stated 8 s and the hard stop at 10 s, timed out on 2 of 8 instances this time and on none before, so its `routeShare` went from 0.886 to 0.658. Deliveries that run close to the stop are where the wall-time limit bites hardest. Options for the user (Phase 2 report): (a) a new routes task version with a CPU-time limit, which ends its bridge continuity; (b) the grader runs each instance three times and takes the median, which keeps the contract and triples grading time; (c) keep it and report the noise.
