## 一、先给结论

**需要整体重构评测设计，但没有证据支持把整个执行框架推倒重写。** 已有版本固定、隔离执行、null-agent、独立 grader、失败归因等基础值得保留。主要需要重构的是：测什么、题目怎样产生、分数怎样形成、怎样确认差距真实存在，以及怎样在未来更新题库。

目前最有证据支持的原因是以下几项叠加：

1. **题目增加了工作量，但常常没有增加新的能力瓶颈。** 一个清楚列出所有规则、可以局部分解、允许查询与脚本求解的任务，变长以后仍然可能容易。模型能执行这些步骤，属于有效能力，不应靠隐瞒规格或刁钻格式来制造失败。
2. **部分评分器的量尺本身容易见顶。** T2 常规工作形成约 72.5 分的高底座；E3 最新版虽然已提高难项权重，但两个模型仍越过了规划质量的最高档。把本地参考解当作 100 分上限，不能保证留有未来空间。
3. **反复围绕很少的题目、模型与同一批反馈调难，没有独立验证“改好了吗”。** 这会使开发集成绩变成调题过程的产物；它不是训练数据污染，但同样损害结论的外推能力。
4. **预算、上下文策略、格式和基础设施改变了成绩的含义。** 高分不必然是 grader 漏判；低分也不必然是推理变难。必须把这些来源拆开。
5. **整个项目的能力覆盖仍偏窄。** 把所有难题都改成组合优化，会把“逻辑、工程、推理、审美”压缩成“会不会写搜索程序”。这不符合项目的原始目标。

此外，本次确实找到一个 T2 评分漏判：未知请求编号下的额外账务操作可能被忽略，错误终态仍能满分。已离线复现，但检查所查 pilot 的 7 份审计日志，没有发现利用该路径的记录。因此它必须修复，却不能被当作该轮高分的已证实原因，详见第三节第 7 项。

**30–80 分可以作为开发期观察窗口，不能成为强制产出的数字。** 所有模型都得到 60 分也可能毫无区分度；94 分与 98 分如果在大量独立题上稳定复现，也可能有信息。应当追求：分数有明确含义、跨模型差距能在保留集复现、重复运行的不确定性足够小、上方仍有有意义的挑战。

## 三、为什么多轮提难仍然失败

### 1. 把“阅读并执行复杂说明”当成了全部高阶能力

T1 的 F 级任务约 190 个小文件、24,000 字符，规则和时间关系能逐项查清；T2 的财务手册明确给出规则与舍入；E3 把功能演进拆成连续发布的阶段。它们并非没有价值，只是主要测量确定规则下的执行、状态跟踪和一致性。

T1 已经做过多链、反事实和历史还原，T2 也已经做过耦合与优化。因此，“再加多跳”“再加干扰项”“再加条件分支”不是新的建议。应追问：这一次到底新增了什么此前不会、不能直接局部求解的能力？

项目 `docs/design/FRONTIER_TASKS.md:7` 把现象概括为模型能够精确执行任何给定程序。这个结论过强。当前证据最多支持：**这些模型在这些任务分布及工具条件下，已经可靠掌握了所测试的程序。** 明确规格依然可以定义非常困难的问题；困难不应来自含糊要求。

### 2. 小规模优化可以被通用求解手段直接攻克

T2 0.2.0 支付选择被 `itertools.combinations` 枚举；0.3.0 的付款排程被随机重启、模拟退火和局部搜索求解。此时增加订单数不保证增加难度：可能只是让模型换一个成熟求解器。

“NP-hard”是问题族的最坏情况性质，不是当前实例的困难证明。题目真正需要的是：在允许的工具和资源内，简单策略、成熟通用算法、人工专家方案之间存在足够且可复现的性能差距。

参考解的作用也应拆开：一个负责验证合法性，另一个负责提供强性能锚点。验证器可以精确判定一个方案是否合法，而不必知道全局最优解；只有小实例证明了最优，不能把所有大实例的最好已知解都叫作最优。

### 3. T2 的分数结构让高分成为常态

当前每个财务日有 44 个内容检查：7 个付款计划梯级各权重 2，其余 37 项各权重 1，总权重 51。假定常规操作和其他相关要求均通过：

| 付款计划水平 | 总分 |
|---|---:|
| 到期日基线，未过优化梯级 | 37/51 = 72.55% |
| 贪心基线，过 25、50 两档 | 41/51 = 80.39% |
| 达到 0.90，过前五档 | 47/51 = 92.16% |
| 达到 0.97，仍未达到最优 | 49/51 = 96.08% |

这不是计算错误，而是量尺的设计结果。只要把常规操作全部做好，真正有难度的优化就很难把总分拉开。继续加更多常规请求，还可能增加这个底座。

证据：`task-library/calibration/t2-finance-desk/private/finance.py:502`；`task-library/calibration/t2-finance-desk/manifest.json:1486`；校准记录也直接列出上述基线分数。

建议把“财务操作正确性”“规划合法性”“规划效用/遗憾值”分栏报告。若需要家族总分，先按能力构成设固定权重，不按检查数量自然累加；新旧分数必须分版本保存。不要事后改权重，只为了让 DeepSeek 落到 80 分以下。

### 4. E3 已修复旧权重问题，但上端仍然太近

旧版 E3 难速度项只占很少检查，这个历史问题已经被修正。当前是 50 项正确性各权重 1，加上 4 项速度、6 项规划质量各权重 5：正确性 50%、速度 20%、规划质量 30%。不能继续拿旧权重批评当前实现。

真正剩下的问题是上端锚点：一个“按依赖路径排序、小实例穷举”的参考方案已达归一化 0.938，而最高规划梯级只有 0.97；最新两个模型都越过最高档。其后再好的规划也不会增加这一部分分数。

应保存原始目标值、合法率、与强基线的差距，以及各类实例的结果，不能只保留过了几个门槛。近最优与超过参考解也需要可观察；最好已知解可以更新，但必须建立新版本，不能追着提交结果改旧榜单。

同类问题不只在 E3：E2 routes 把每个实例的连续收益压成 50/80/90/97% 四档；E4 的速度与压缩也使用梯级。所谓“连续目标”经过这些检查均分后，仍然是离散量尺。一个合法 speedup 程序跨过首档时可一次拿到 4/8 分，compress 跨过首档时可拿到 3/6 分。台阶可作为达标标签，但主报告还应直接给出运行时、压缩字节数或目标差距。证据：`task-library/calibration/e2-spec-implementation/rubric.md:10`；`task-library/calibration/e4-terminal-tasks/rubric.md:7`、`:31`。

### 5. 局部容错与全局成功不是同一个指标

T2 每个请求以模型自己的前序操作形成的起始状态为基准运行 oracle。这能避免一个错误被重复扣分，是有意设计，不能直接称作 bug。但是，“后续操作对当前账本正确”不一定意味着“整天业务最终结果正确”。

建议并列记录两项：局部诊断分继续保留；另加从原始状态出发检查全流程终态、不变量和关键业务目标的成功率。这样既能定位错误，也能判断是否完成真实工作。全局成功失败不应抹去所有局部诊断信息。

同样，E3 当前 `contextPolicy` 为 `per-stage`，前后阶段继承项目文件，但不再共享完整会话。它主要测跨阶段代码演进，不能与旧版连续会话结果混合，声称在测同一种长上下文记忆能力。

### 6. 预算造成的低分，必须按事先约定解释

从 T2 该轮原始请求用量重算，6 个试验中 5 个的缓存读取占计量 token 约 92–98%；MiMo fn1 的早退试验约为 56%。校准文档把这一范围写成每个试验都适用，并不严格准确。相同 total-token 配额会同时约束上下文重复传输、工具轨迹和输出，不能简单称作相同推理量。E3 调整上下文策略和阶段预算，也显著改变了结果。原始用量见 `runs/suites/20261023-050438-dev-9f16/runs/T2/4c66fddb-9494-4491-808c-fcd5164c15fa/report.json` 的 `execution.requestUsage`。

固定预算下无法交付可以是有效失败；开放优化跑满预算也完全正常。关键是先说清楚测量目标：

- 固定预算赛道：预算内最佳可交付成果就是成绩，模型自身无效循环不能随意排除。
- 预算曲线：用预先定义的 B、2B、4B 等条件观察质量增长与平台期，作为补充分析。
- 宽裕预算赛道：先校准预算，再冻结；不能看到某模型失败就无止境加额度。

继续保留用户已确定的 token 计量方式，同时单列输入、缓存读取、输出、可获得的 reasoning token、调用次数、运行时间、工具计算资源。它们是诊断信息，不要求擅自改成价格计分。不能跨供应商假设所有隐藏推理量都可观察或可对齐。

### 7. 只复盘失败，会漏掉“假阳性满分”

项目已经认真修复过很多误扣分问题，也有 null-agent 和 mutant 校准。这些值得肯定，但零提交得零分，只能排除最粗的漏洞；参考实现全过，也不证明测试足够完整。

下一轮首先应审计高分提交：它是真正确，还是恰好满足有限检查？对已固定的规格，冻结历史提交，用独立边界测试、性质测试、状态序列和合法替代实现复核。新增需求不许倒扣旧分；对合法的新测试，另记审计结果，再决定版本化重评分所有模型。

**本次已复现的具体漏判：T2 未知请求绕过操作覆盖。**

- `task-library/calibration/t2-finance-desk/private/ledger.py:237` 只检查 `begin` 的编号符合 `R[0-9]+`，所以接受 `R999`。
- `private/finance.py:447` 的分段逻辑把随后的操作放入这个未知请求；`:516` 起的评分循环只遍历题目合法请求。
- 在正常完成 fn1/fn2 后，追加 `begin R999`，再追加借记 1100、贷记 4000 各 1,000,000 EUR 的账务操作。通过内存模拟交付给完整 `grader.grade`，得到 `integrity=consistent`、45/45 检查通过，而账簿终态已错误。这里 45 项包含格式检查，与前述 44 项内容检查不矛盾。
- 完整性检查只能证明账簿与操作日志相符；当评分漏掉某类操作，它不能证明业务正确。
- 对 `runs/suites/20261023-050438-dev-9f16/runs` 下 7 份审计日志的只读扫描，没有未知请求，也没有首个 `begin` 前的操作。这一漏洞没有解释本轮实际 98–100% 成绩的证据。

P0 修复应增加“每条变更操作必须归属于唯一合法请求”的覆盖不变量，对未知编号、未归属操作、重新开启与乱序请求制定明确策略，并为它们加入负例。然后统一重放相关历史提交。不能只禁止字符串 `R999`，否则同类未覆盖操作仍会存在。

本次抽查没有建立“私有答案泄漏、路由到同一模型、缓存串题导致全部高分”的证据。默认 sandbox、`trustedLocalExecution` 和 grader 的使用方式不能直接当作泄漏证据。上述可能性应通过运行证据检查，而非作为已知根因写进结论。

## 四、整体重构：以能力矩阵组织题库

建议保留现有 ID 以便追踪，但在报告上建立三层：基础可靠性、能力区分、前沿挑战。基础可靠性允许高分；主要模型差异来自能力区分层；前沿层为未来保留空间。比例可以在开发期调整，但发布后必须冻结，不能承诺某个混合比例必然产生 30–80 分。

| 现有家族 | 建议定位 | 下一步真正值得新增的内容 |
|---|---|---|
| T1 证据恢复 | 保留为证据使用与合规基线 | 不同领域的独立证据任务；检验冲突来源的优先级、缺失证据下的正确弃答、反事实是否改变结论。保留“只给现有工具”的协议，不假装它是可任意写脚本的任务 |
| T2 服务/财务工具 | 分开测操作可靠性与决策 | 固定工具状态机；重复请求、部分执行、状态改变后的恢复与重新规划；若加入不完全信息，必须给可查询信息源或明确允许澄清，不能靠隐藏要求判错 |
| R3 逻辑网格 | 保留已有信号，扩充推理覆盖 | 增加可验证证明、反例、不可满足性证书、规则迁移等独立题型；把无工具推理与允许求解器的代理任务分成两个协议。格子更大不是唯一难度轴 |
| E2 规格实现/优化 | 保留有效题，扩大任务种类 | 跨模块实现、协议兼容、数据语义、异常恢复；优化只占一部分，独立测功能正确性与目标收益 |
| E3 长周期维护 | 从一个教学式项目扩展到项目分布 | 在多个真实或经过审校的代码库中做定位、修改、迁移、回归防护；构建跨阶段依赖和真实设计取舍，而非每阶段都明示应该怎么改 |
| E4 终端/性能 | 保留压缩等有信息任务，重校速度项 | 使用未知但明确格式的数据分布、工具诊断与系统恢复；性能测量固定机器/资源、预热、重复并报告噪声，必要时把性能与正确性分开 |
| VIS 审美/前端 | 单独作为视觉能力维度 | 至少覆盖信息密集界面、编辑类页面、表单流程、不同品牌目标和移动布局；功能验收必须执行交互，审美采用盲评与人工校准 |
| AE 算法工程 | 前沿层候选，等待实测 | 保留官方目标值与人类性能参照，增加不同结构题族和新保留实例；不能代替全部工程或推理能力 |
| LR / Commit0 | 有价值的备选工程轨道 | 按模块/能力分组验收，控制公开源码记忆和测试数量失衡；从少数项目验证成本与有效性，再扩规模 |

每个新任务必须写一张“能力卡”：测什么、不测什么；允许什么工具；任务真正难在哪里；最便宜的捷径是什么；参考与替代方案；隐藏测试对应哪些公开要求；采用什么评分单位；允许哪些等价解。写不出“真正难在哪里”的任务，不应先投入一轮昂贵模型运行。

这里的覆盖漂移已经发生：`suites/full.json:38` 起，E2 只选 routes，E4 只选 speedup/compress。它们与 AE 的重叠比家族名称显示得更大。因此“有很多 family”不能作为覆盖全面的证据。

VIS 也已有匿名、双顺序、同厂回避及 judge exam，不需要从零再造。最新所查正式锦标赛仍有 25% 顺序不一致、76% 同配对裁判一致；考试四名有效裁判全对并不保证真实比较同样稳定。所有作品还围绕同一个 BookLoop brief。应扩展独立 brief，并把当前按 games bootstrap 的区间改为考虑 brief/页面与重复裁判的相关性；同一个页面被评很多次，不等于有很多独立作品。证据：上述 `visual/tournament.md:11`、`:17`、`:21`；`experiments/vis-calibration-2026-10/README.md:3`。

三类原型值得优先做，小规模验证即可：

1. **工程恢复原型**：给已有服务、日志和数据，要求修复“重试时产生重复操作”等跨模块问题。规格明示幂等性、兼容性和恢复要求；隐藏测试枚举故障插入位置与操作序列。测因果定位和全局不变量，而不是能否把指令翻译成函数。
2. **工具规划原型**：在有查询接口、明确约束和状态变化模型的模拟系统中分配资源。关键是观察后重规划、避免重复副作用和满足终态目标；真实未知信息通过工具获得。若采用随机事件，固定并配对事件种子，避免模型遭遇不同难度。
3. **推理原型**：提供未见规则体系，让模型给出结论及机器可检验证书；同时包括成立、不成立和信息不足。小实例由独立求解器确认，题族按推理结构留出，不能只替换人名数字。

这些是待验证的设计假设，不承诺一上来就能压低强模型成绩。如果一个简单脚本已能稳定解决全部原型，应先改变测量问题或将其归为基础层，而不是再添加二十条细则。

| 来源 | 可借鉴的方法 | 对本项目的约束 |
|---|---|---|
| [FrontierMath](https://arxiv.org/abs/2411.04872) | 专家原创题、独立审校、可自动验证的答案 | 难度来自内容与专家验证，不能靠命名“专家级”或把现有题写长；数学也不能代表审美和工程全部能力 |
| [EvalPlus](https://arxiv.org/abs/2305.01210) / [代码](https://github.com/evalplus/evalplus) | 加强测试能揭示旧评测漏过的错误，并改变排名 | 先拿已有满分答案做独立压力测试；更多测试必须仍符合原规格 |

## 七、怎样验证重构真的有效

### 1. 先分离开发集与评估集

建立三份互斥集合：开发集可反复看失败；验证集用于冻结前选择一次；保留集用于冻结后的正式验证。既按实例分，也按题族/项目/结构分，避免同一个生成模板的不同随机种子同时出现在两边。

不同模型使用同一固定协议和成对实例。开发期可以继续使用现有低成本模型限制；正式验证若需要新增档位或供应商，另列成本方案。不要把只对 DeepSeek 调出的题库叫作通用能力量尺。

### 2. 评分单位从“测试条数”改成“任务和能力”

一个项目有 1,000 个高度相似测试，不能因此比另一个项目的 30 个重要场景权重大三十倍。建议先按业务能力/行为分组，组内测试用于判定正确性，再按预先定义的组权重计算任务分，最后在独立任务间平均。

保留三类输出：完整解决率、诊断性部分分、连续目标原值。格式合规单列；如兼容旧版仍保留扣分，同时展示扣分前后的结果。E3 的一次轨迹不是 60 个独立样本，R3 一题的格子也不是几十道独立推理题。

例如 R3 的 9×9 网格若只交换两个格子，单元格准确率仍是 79/81≈97.5%，完整解却错误。现有实现已记录 resolved；应在主表把完整解率、单元格准确率和约束有效性并列，避免把局部正确率读成解题成功率。见 `task-library/calibration/r3-logic-grid/rubric.md:7`、`private/grader.py:63`。

### 3. 运行协议是成绩的一部分

至少记录任务 hash、grader 版本、代码提交、模型提供方/ID/可得快照信息、thinking 配置、temperature、工具与软件环境、预算、会话策略、重试选择规则、终止原因和原始分项值。

基础设施失败显示缺失和覆盖率，不能记成模型零分，也不能静默删除后只报成功样本。模型自身的超时、循环或未交付按冻结规则记分。修复 grader 后保留旧结果和新结果，并对相关模型统一重评分；不只给某个模型挑最好的一次。

### 4. 小样本用于筛题，正式结论需要独立样本

一个可执行的起步方案是：每个需要重建的能力先做 6–10 个开发实例，来自至少 3 种结构；冻结后用 20–30 个新的独立任务做初轮验证，关键模型每题 3 次。这个规模是工作建议，不是统计充分性的保证；项目成本很高时可以先少做，但必须把结论标为探索性。

优先增加独立任务覆盖，再决定重复次数。模型差距只有几分、或任务相关性高时，需要更多样本；重复同一个项目几十次不能替代更多项目。

报告每个模型对的逐任务差值及区间，按任务/题族聚类，而非把每个断言当独立伯努利试验。现有 `pairedDifference` 可以复用或扩展；小样本时不要把任何形式的区间当作可靠排序保证。E3 当前 n=1，只能说明这一条轨迹结果不同。

### 5. 发布门槛围绕可信度，不围绕压分

建议冻结前逐项回答：

- 满分提交经独立测试仍然正确吗？是否存在明显错误却拿高分的提交？
- 合法替代实现会被错误拒绝吗？所有隐藏检查都能追溯到公开任务契约吗？
- 开发集上的差距在保留题族上还存在吗？差距是否主要来自格式或基础设施？
- 至少部分任务的简单策略、较强基线和专家方案有实质性能差距吗？
- 继续增加计算预算时，是质量提高、已经平台，还是主要增加重复上下文开销？
- 题库覆盖是否仍符合逻辑、推理、工程、审美四个目标，而非只覆盖优化搜索？

若答案是否定的，修相应问题；不要通过线性缩放、榜内归一化或临时加门槛把分数塞进目标区间。

## 九、留给实现者的判断准则

看到 100 分时，先判断满分代表的契约是否完整、答案是否真通过；答案真正确，就承认这部分能力已经被掌握，保留它作为基线，再拓展任务分布。看到 40 分时，先判断损失来自模型能力、预算协议还是评测缺陷。

最需要停止的循环是：**同一题族 → 再加规则/规模 → 在同一批模型上跑 → 仍高分 → 再加规则。** 替代它的流程是：**能力定义 → 独立任务与强基线 → 成功/失败双向审计 → 冻结协议 → 保留集验证 → 版本化扩展。**

本项目下一阶段最有价值的成果，不是一张“终于都落在 30–80 分”的表，而是一张能够回答“这些模型到底在哪种能力上稳定不同，以及我们为什么相信这个差距”的证据表。
