# PLAN-007 Phase 1: the measurement layer

Started 2026-10-24. No paid model runs. One note per work package, in the order they were committed.

## WP1.3 `src/scoring/`

Written first, because the manifest v2 score model (WP1.1) uses its types.

- `anchors.ts`: piecewise-linear normalisation through declared anchor points; below the lowest anchor the first segment continues down to the floor of 0; above the highest the last segment's slope continues without a cap, flagged `extrapolated`. Lower-is-better metrics (bytes, runtime) work in "goodness" units. Anchors must improve strictly in both mapped value and raw value, or the normalisation refuses.
- `model.ts`: the score model types (`primary`, `groups` with rules `all`, `fraction`, `metric`, `metrics` with anchors, `format`, `structureCap`) and `buildOutcome`, which turns a grader verdict, its raw metrics and the execution into the task outcome record of MEASUREMENT §2:
  - `resolved` = every critical group passes in full;
  - `diagnostic` = Σ weight·score / Σ weight, a metric group weighing its normalised value within [0, 1];
  - `primary` = resolved (0/1), or the uncapped normalised metric of a valid delivery;
  - `format` = `strict`, `recovered` or `missing`, with the PLAN-005 deduction as a separate `penalised` value (decision D2 still open; the headline is content);
  - `stop` by kind, `usage` by token kind (a field a provider does not report is null, never 0), and `coverage` (`unscored` with a reason for infrastructure failures, provider refusals and grader errors; never a zero).
- `aggregate.ts`: per-task means over repetitions; family means with equal task weights and structure caps (a group above the cap is brought down to it and the rest shares the remainder by tasks; with too few groups for the cap to hold, groups weigh equally); capability means with declared weights; saturation indicators (solved by all, solved by none, best above the strong anchor, spread).
- `bootstrap.ts`: a seeded cluster bootstrap over structure groups (2,000 resamples, percentile 95%), "n too small" below five groups; paired comparisons by task with the same capped weights, the share of tasks each model is ahead, and the existing `pairedDifference` t interval as a cross-check.
- Tests: `tests/scoring.test.ts` (uncapped and floored anchors, extrapolation flag, lower-is-better, refused anchors; group rules, resolved, format statuses, unscored coverage, stop kinds; structure caps and the equal-groups fallback; repetitions and saturation; seeded bootstrap, "n too small", paired comparisons).

## WP1.1 Manifest v2

- `src/evaluation/manifest-v2.ts`, called from `validateTaskPackageManifest` for `schemaVersion: 2`. Every v1 rule still applies; the v2 fields are checked as strictly: unknown keys refused at the top level and in items; `tier` (basic, core, frontier); `capabilities` (engineering, reasoning, agentic, visual); the `card` must be a hashed trusted file; the `scoreModel` (primary, groups by rule, each check in exactly one group, metrics with strictly increasing anchors, a non-critical format check, the structure cap); per task a `split`, a `structure` group, `provenance` (source, date, licence, exposure) and a raw value for every anchor of every anchored metric; no structure group in two splits; groups covering every check a task is graded on; `runtime.mounts` under `runtime/` with safe environment names. `scoring` (v1) and `scoreModel` (v2) never appear together, and a v1 manifest with any v2 field is refused.
- Design addition (CODE §3.1 updated): a package without items is one task, placed by a top-level `task` object.
- `scripts/task_packages.py` mirrors the v2 rules that matter offline: card hashed, splits and structure groups present and disjoint, anchors complete, groups covering every graded check.
- Tests: `tests/manifest-v2.test.ts` (a complete v2 manifest; sixteen refusals; an item-less v2 package; every v1 package in the library still loads).

## WP1.2 Grader result v2

- `src/evaluation/grader.ts` accepts `schemaVersion: 2` results, which add `metrics`: a list of `{id, value, unit?}` with identifier ids, finite numeric values and no repeats. A completed grading must report every metric the manifest's score model names (`GRADER_METRIC_MISSING`), so a v1 result cannot satisfy a v2 open-ended task; other metrics are kept as diagnostics. The metrics travel on the evaluation (`EvaluationResult.metrics`) into `score.json` and `result.json`. v1 results are unchanged.
- Tests: `tests/grader-v2.test.ts` (metrics carried; a missing required metric, a non-numeric value and a repeated id refused; a v1 result against a metric score model refused).

## WP1.4 `outcome.json`

- `src/scoring/outcomes.ts`: `writeOutcome` builds the outcome record (WP1.3) for a v2 package and writes it beside `score.json` in the score run it was computed from; a v1 package gets none. `loadOutcomes` returns each trial's latest outcome in a run directory and leaves out trials a resumed batch superseded.
- Written by every path that appends a score run: a run (`run.ts`), a re-grade (`regrade.ts`, into the pending score run before it is committed), a trajectory (`trajectory.ts`, in the score run of the last graded snapshot, with the whole trajectory's execution, since the trajectory is one task) and a trajectory re-grade (`trajectory-regrade.ts`, when it re-grades that last snapshot).
- The item's split, structure group and anchor values come from the manifest (or its `task` object), the model label carries the thinking level, and the grader version is the manifest's.
- Tests: `tests/outcome.test.ts` (a v2 fixture run writes one outcome per trial, uncapped above the strong anchor; a re-grade under grader 1.1.0 appends a second outcome, the first stays, and the run's latest outcomes follow the re-grade).

## WP1.5 Report v2 and suite v2

- **Suite v2** (`src/suite/spec.ts`, CODE §3.4): `schemaVersion: 2` with `release`, `split`, `capabilityWeights` (only core families of that capability) and `composite: null` (decision D3); every family names its `tier` and `capability`; the v1 `target` is refused. v1 suite files are unchanged and keep the v1 report.
- **Plans run one split** (CODE §3.3): plans take an optional `protocol` (`track` fixed or curve, `split`, `label`); a holdout plan must be on the fixed track; preflight refuses a plan whose v2 tasks mix splits or differ from its protocol's split. A v2 suite narrows each v2 family's template to the suite's split and records the protocol in the generated plan. The plan's `repetitionSubset` (validation runs) is left for Phase 5, when it is first used.
- **Null-agent smoke for v2 families**: every outcome of the smoke run must be scored, unresolved and at a primary of 0.
- **Report v2** (`src/analysis/report-v2.ts`, MEASUREMENT §7), built from the outcome records of v2 families and written as `report-v2.json`; `report.md` holds the v2 report and then the v1 report (run details, phases, tokens, and any v1 families). Contents: the header with split, track, models with thinking and temperature, and each family's budget, context policy, tools and command limits; the label "exploratory" for a dev split or any family with fewer than five structure groups; the capability profile (core families combined with frozen weights, a stratified cluster-bootstrap interval, task counts) with basic and frontier rows apart; family tables (tasks, trials, coverage against planned tasks with "incomplete" below 90%, resolved rate, primary with interval, diagnostic, medians of raw metrics, format counts and the penalised value, stops, infrastructure failures and refusals); pairwise comparisons per core capability; saturation and headroom; efficiency (reported, not scored); and the latest success audit per family. Seeds derive from the suite id, so a rebuilt report gives the same intervals.
- `src/scoring/bootstrap.ts` gained composable resamples (`familyResamples`, `combineResamples`, `intervalOf`) for the capability layer.
- Tests: `tests/report-v2.test.ts` (a golden file, `tests/fixtures/report-v2.golden.md`, whose numbers were checked by hand); `tests/suite.test.ts` (a v2 suite with a v2 and a v1 family: only the split runs, the v2 smoke reads outcomes, `report-v2.json` holds the v2 family and `report.json` the v1 one; refusals of mixed splits, a mismatched protocol, a holdout curve, a v2 target and misplaced capability weights).

## WP1.6 The layer on two real families

- self-calibration 26/26 (`logs/self-calibration-0.2.0.log`), including every naive reference on its anchor and the extrapolation above the winner.

**Deviation, recorded.** Writing naive references for the six validation problems meant reading their statements, while VALIDATION §3 says validation contents are not opened while designing. TASK_LIBRARY §3.6 asks for references for every problem, and a reference is an anchor, built the way an ER gold patch is validated; nothing about the tasks or their grading was tuned on them. The AE card states this.

**Proof** (`scripts/measurement-proof.ts`, `docs/evidence/v2-proof/report-v2.md`): one report v2 over R3 (the re-graded pilot) and AE (reference programs graded through the real grader protocol as pseudo-models). It shows the resolved headline with output-limit stops in their own column (mimo-pro: 14 of 24 R3 trials), provider refusals as unscored rather than zero (mimo-flash: 2), the uncapped normalised AE performance (AHC039 grid reference 1,547 → 0.551), intervals where a family has five structure groups or more (AE naive references over ten contests) and "n too small" where it has three (R3 grid sizes), saturation and headroom, and pairwise comparisons.

Fixes made while reading the proof report:

- score groups count only the checks a task is graded on (`expectedCheckIds`): R3 items of different sizes share one group of 100 cells, and a trajectory still fails the checks of stages it never reached;
- report v2: pairs of models with no shared task are left out; saturation reads only the models that took part in a family; raw metric medians keep three decimals; the resolved column is weighted like the primary (structure caps), so the two agree for a resolved-primary family;
- `manifest-v2.ts` accepts the v1 `generator` key.

## Phase 1 summary

- Done: WP1.1–WP1.6. Tests: 105 outside the trajectory file, all passing; the trajectory file is run once at the end of the phase.
- The layer works end to end on real data: a v2 package → a v2 grader result with metrics → an outcome record beside every score run (runs, trajectories, re-grades) → report v2 with a capability profile, intervals over structure groups, saturation and audit status.
- Left for later phases, as planned: plan `repetitionSubset` (Phase 5); the `none` tool profile and R3's formal switch to it (WP2.4); R3's validation and holdout items (WP2.3); AE's greedy references and fresh seeds (WP3.5).
- For the user: nothing new to decide. D2 (the format deduction) is shown as the planned separate `Penalised` column, with content as the headline, until the user decides.

Addendum to WP1.6: the evidence table (`npm run evidence`) now reads a score run that carries `outcome.json` by its outcome: the row shows the mean v2 primary, marked "v2 primary", never a v1 partial-credit score (MEASUREMENT §8). The R3 pilot thus has a grader 1.0.0 row (v1 partial credit, e.g. deepseek 72.3%) and a grader 2.0.0 row (v2 primary, the resolved rate: deepseek 0.708). The evidence table weighs trials equally within a run; report v2 applies structure caps, so the two can differ slightly (mimo-flash 0.292 against 0.304).
